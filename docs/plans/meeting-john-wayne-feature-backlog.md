# PathQuote — беклог фіч з мітингу (Джон + Вейн)

Дата аналізу: 2026-09-01. Джерело: транскрипт демо + твоє зауваження про базову ціну машини.
Код не писався. Кожен пункт: **що**, **чому** (звідки в транскрипті), **що саме робити**, **розмір**.

Позначки розміру: `S` = години, `M` = 1–2 дні, `L` = тиждень+, `XL` = окремий великий модуль.

## P0 — Баги / дрібні, робити зараз

### 1. Показувати базову ціну машини (твій баг)
**Чому:** Вейн прямо: *"we have included options, but we don't have the base model"*. Зараз у рядку товару видно одну суму = база + опції.

**Фактичний стан у коді:**
- `DocSheetItem` **вже несе** і `unitPrice` (чиста база), і `total` (база+опції−знижка) — `src/lib/sheet-data.ts:480`.
- Рендериться база **лише** в розширеній квотації: `src/components/sheet/quotation-sheet.tsx:325`, і то субтотал рядка з'являється тільки якщо є опції.
- Губиться в: `src/components/sheet/document-sheet.tsx:176` (інвойс + summary-лист друкує тільки `item.total`) і в білдері `src/components/builder/items-list.tsx:262`.
- `{{price}}` у шаблонах описів теж підставляє `total`, не базу — `src/lib/quotation-data.ts:582`.

**Робити:**
1. У `document-sheet` (інвойс/summary) рядок товару розбити на: `Base price` → список опцій (якщо `showOptionPrices`) → `Item subtotal`. Тобто та сама структура, що вже є в quotation-sheet.
2. У білдері поруч із сумою рядка показувати `Base` малим шрифтом.
3. Додати окремий плейсхолдер `{{basePrice}}` на додачу до `{{price}}`, щоб у описах можна було вказати саме базу.
4. Переконатися, що при `showOptionPrices = false` видно: базу машини + загальний субтотал позиції (без розшифровки опцій) — саме цього хотів Джон («не показувати ціни опцій, але тотал по позиції лишити»).

Розмір: **S**

### 2. Кількість (qty) на рівні позиції-машини
**Чому:** Вейн: *"you might want to have here the detail of the quantity"*; сценарій «два M + один X в одному квоті».

**Стан:** `DocumentItem` **не має** поля `qty` — позиція завжди = 1 (`prisma/schema.prisma:280`, `src/lib/pricing.ts:214`). Qty є лише в `DocumentLine` (опції/столи).

**Робити:**
1. Міграція: `DocumentItem.qty Int @default(1)`.
2. `computeTotals`: `itemBase = qty * (unitPrice + Σ lines)`. Обережно: знижка по позиції застосовується після множення.
3. UI: поле qty на картці позиції; у квотації показувати `2 × M5180` і `Unit / Total` колонки.
4. Перевірити всі місця, де рахується сума (пошук по `itemTotals`).

Розмір: **M** (зачіпає pricing + всі рендери)

### 3. Дата «дійсна до» у блоці Total Investment
**Чому:** Джон: *"there is no date, valid to"* + *"put the valid-to in this total investment line, so it's obvious"*.

**Стан:** `validityDate` рахується (`src/lib/sheet-data.ts:493`) але записується тільки при фіналізації і виводиться не там, де треба.

**Робити:**
1. Показувати `Valid until: DD Month YYYY` прямо в блоці Total Investment (перша сторінка), не лише в шапці.
2. Дозволити перевизначити кількість днів **на конкретному квоті** (зараз тільки глобальний сеттінг `quote.validityDays`): поле в білдері, дефолт з налаштувань, м'який ліміт 30 днів + попередження при більшому (Джон: іноді 6–8 тижнів під CAPEX-процес клієнта).
3. Для драфту показувати «Valid for N days from issue».

Розмір: **S**

**Чому:** Джон: *"Put pages, numbers"*.

**Робити:** футер Gotenberg: `Q-AU-2026-001 · Page X of Y · Pathfinder`. Перевірити на обох PDF-роутах.

Розмір: **S**

### 5. Дозволити від'ємну ціну в extra lines (trade-in)
**Чому:** Довга дискусія про trade-in: машина 195k → показати 210k, дати 15k trade-in. Вейн запропонував саме extra line з мінусом, Джон погодився: *"Now, can you allow it to be a negative? Wow, that means we can write trade-in there... K5 390, serial number, customer responsible for removal"*.

**Стан:** валідація **забороняє** мінус — `src/lib/validation/documents.ts:53,66` (`NON_NEGATIVE_AMOUNT_REGEX`).

**Робити:**
1. Дозволити від'ємний `unitPrice` для `kind: CUSTOM` extra line (для опцій/продуктів — залишити заборону).
2. У квотації такі рядки рендерити окремим стилем (наприклад `− $15,000.00`, зелений/курсив), і **не** пускати в production forms (див. п.15).
3. Валідація: субтотал документа не може стати < 0.
4. Опційно — пресет «Trade-in» з полями model / serial / removal responsibility, що збираються в опис рядка.

Розмір: **S**

## P1 — Потрібно до реального запуску

### 6. Адреса доставки / інсталяції
**Чому:** Джон: *"in our order forms we always have: where is the machine actually going to be delivered"*.

**Робити:**
1. `Company`: блок delivery/install address (окремо від billing), + прапорець «same as billing».
2. На документі: `deliveryAddress` — дефолт з компанії, можна перевизначити для конкретного квота (клієнт може мати кілька майданчиків).
3. Виводити в квотації і обов'язково в order forms.

Розмір: **M**

### 7. Вибір юрособи-продавця + реквізити банку
**Чому:** Джон: UK-ентіті може продавати самостійно, але платіж іде в AU; LLC шле квоти з Indianapolis. *"Can you make a selection of two different types of bank details?"* + *"only the super admin can change bank details"*.

**Стан:** реквізити/логотип/адреса є в `Region`, але один комплект і немає вибору на документі.

**Робити:**
1. Нова сутність `BankAccount` (кілька на регіон): назва, банк, IBAN/BSB/SWIFT, валюта, `isDefault`.
2. На документі: селектор `issuingEntity` (регіон-продавець) **окремо** від регіону клієнта + селектор `bankAccount`.
3. Обидва потрапляють у `entitySnapshot` при фіналізації (щоб історія не «попливла»).
4. Редагування банківських реквізитів — тільки ADMIN/super admin; менеджер лише обирає з дозволених.
5. Поле Incoterms / delivery terms на квоті (`Ex Works` / `Delivered to site` / custom) — Джон окремо це підняв щодо UK.

Розмір: **M–L**

### 8. Обов'язкові конфігураційні поля (left/right тощо)
**Чому:** Джон: *"you should not be able to create the quotation without specifying this"* — сторона (left/right), розмір ножа й інші поля, що зараз є тільки в order forms.

**Робити:**
1. У каталозі позначати опції/атрибути прапорцем `required` (+ `defaultValue`, бо Вейн: *"it should default to what is standard"`).
2. Валідація на finalize (`src/lib/validation/finalize.ts`): не фіналізувати, поки не заповнені всі required-атрибути кожної позиції; показувати чіткий список того, чого бракує.
3. У білдері — бейдж «Configuration incomplete» на картці позиції.
4. Перенести в каталог поля, які зараз існують лише в паперових формах (сторона, довжина столів, knife size тощо).

Розмір: **M**

### 9. Дефолти й чистка каталогу
**Чому:** *"you probably need to get rid of all those edge strips, we don't sell them"*; *"Fabric Pro side should default to standard"*; *"everything should have a part number"*.

**Робити:**
1. Поле `partNumber` на продуктах і опціях; виводити в квотації (дрібним) і в order forms.
2. `isDefault` / `isStandard` на опціях — автододавання при виборі продукту.
3. Прибрати/приховати неактуальні позиції (edge strips і т.д.) — прапорець `active`, а не видалення (щоб старі квоти не ламались).
4. Іконки для опцій — вже є, доповнити.

Розмір: **S–M** (плюс дата-робота Мартіна)

### 10. RSP / RSP Plus як продукт
**Чому:** Обговорення remote support: включати завжди, показувати вартість, зробити частиною контракту (perpetual agreement, CPI cap, включає софт-апдейти).

**Робити:**
1. RSP і RSP Plus — звичайні продукти в каталозі з ціною по регіонах (можливо, % від ціни машини — потрібно рішення Роя/Джона).
2. Автододавання RSP-рядка в кожен квот (можна прибрати вручну; якщо прибрано — сума 0, але T&C лишаються).
3. T&C по RSP уже статично в квоті — лишити, доповнити текстом про щорічне поновлення та CPI.

Розмір: **S** (сама фіча) — блокер: цінова політика

### 11. Зображення: кілька на продукт + hero на першій сторінці
**Чому:** *"imagine if for that product there were 2 or 3 pics and you could just hit the one you wanted"* + *"put a complete image of the solution — M + easy loader + fabric pro all in one line — on the first page so I can see what I'm buying"*.

**Робити:**
1. `ProductImage` — галерея на продукт; на рядку квота вибір, яке зображення показати (дефолт — головне).
2. Опційне «hero / solution image» на першій сторінці квота: салес обирає з бібліотеки або завантажує своє + короткий підпис.
3. Перекомпонувати першу сторінку: hero-картинка → Total Investment (нижче/по центру, а не зверху) → Valid until. Розшифровка з 2-ї сторінки.

Розмір: **M**

### 12. «Create new quote from this» (ревізія)
**Чому:** Джон боїться unfinalize існуючого: клієнт може повернутись зі старим PDF. *"Let me add one single button — create a new quote based on this. Yes, that's it."*

**Робити:**
1. Кнопка «Duplicate / New revision» на документі → новий DRAFT з копією всіх позицій, ліній, знижок, нотаток.
2. Зв'язок `sourceQuoteId` (поле вже є) → показувати «Revision of Q-AU-2026-001» і ланцюжок ревізій.
3. Опція «перерахувати за поточним прайсом» vs «зберегти ціни оригіналу» — при копіюванні запитувати.
4. Unfinalize лишити тільки для ADMIN (як зараз).

Розмір: **S–M**

### 13. Пошук і фільтри по документах
**Чому:** *"I've got 200 companies and probably 1000 quotes — how the hell am I going to find it again"*.

**Робити:**
1. Пошук по: назві компанії (частковий збіг, не тільки початок), номеру квота, контакту, коду продукту, серійному номеру.
2. Фільтри: статус (Draft/Final/Won/Lost), регіон, автор, діапазон дат, сума.
3. Салес бачить свої, ADMIN — усі (перемикач «Mine / All»).
4. Сортування + пагінація.

Розмір: **M**

### 14. Права: видалення й доступ
**Чому:** *"they should not be allowed to delete a quote... but they can delete a draft"*; *"once it was created as a quote, we keep that forever"*.

**Робити:**
1. Менеджер: видаляє **лише власні DRAFT**. FINAL — ніколи.
2. ADMIN: soft-delete/archive для FINAL (статус `VOID`, не фізичне видалення) з причиною.
3. Audit log: хто фіналізував, розфіналізував, змінював ціни/знижки понад ліміт (частково вже логується).

Розмір: **S–M**

## P2 — Наступний великий блок

### 15. Генерація production / order forms з квота
**Чому:** Це те, над чим ти вже почав. Джон: *"the customer ordered based on that quote — generate the order, it generates all the order forms, then it goes to Martin"*.

**Робити:**
1. Мапінг: позиція квота → тип форми (Cutter / Easy Loader / Fabric Pro / Software / Miscellaneous).
2. Easy Loader: змінна кількість столів (1–4, теоретично більше) — кожен стіл окремим блоком із довжиною.
3. Extra lines (у т.ч. з картинкою й trade-in) **не** йдуть у стандартні форми — тільки в **Miscellaneous order form** (Джон: така форма існує, треба взяти оригінал).
4. Зберегти існуючий дизайн паперових форм (Джон: *"I will not change the design"*), автозаповнення полів **над лінією**; поля під лінією (серійний номер, чек-лист) лишаються під ручне заповнення.
5. Вивід: один PDF-пакет на замовлення + окремі форми; прив'язка до документа.
6. Статус документа: `Quote → Order` з номером замовлення.

Розмір: **XL**

### 16. Електронний підпис + захищене посилання для клієнта
**Чому:** *"I can create a thing, you just push the button sign, and it will be like a big screen — you just use a finger"* + потреба закрити цикл «надіслав → підписав → у нас в системі». Плюс вимога не світити ціни назовні.

**16.1. HTML-версія квота за посиланням**
1. Публічна сторінка квота (адаптивна: телефон / планшет / десктоп) — той самий контент, що і в PDF, але як HTML.
2. На сторінці: кнопка **Sign online** і кнопка **Download PDF** (роздрукувати й підписати від руки, або підписати електронно пізніше).
3. Підпис пальцем/мишею на canvas + ім'я, посада, дата; після підпису генерується PDF з вшитим підписом і зберігається до документа.
4. В адмінці статус документа: `Sent → Viewed → Signed by customer` (з датою, IP, user-agent для доказовості).

**16.2. Безпека посилання (магік-лінк для клієнта)**
Вимога: посилання не має працювати, якщо клієнт перешле його третій особі — щоб ціни не розповзались.
1. Токен прив'язаний до email конкретного контакту; сам URL **не** відкриває квот напряму.
2. Клієнт відкриває лінку → сторінка просить підтвердити email → на цей email летить одноразовий код/лінк → відкривається квот у сесії на N годин.
3. Якщо посилання відкрив хтось інший (інший email) — доступу немає, менеджеру приходить сповіщення про спробу.
4. Токени: обмежений час життя, можливість відкликати з адмінки, лог усіх відкриттів.
5. Питання до обговорення: наскільки жорстко — «email-verification при кожному новому пристрої» vs «один раз, далі cookie».

**16.3. Надсилання листа клієнту**
1. Шаблон листа (редагується в Settings, як інший контент): тема, тіло, змінні `{{contactName}}`, `{{quoteNumber}}`, `{{total}}`, `{{validUntil}}`, `{{salesperson}}`, посилання.
2. Кнопка «Send to customer» на документі → лист із посиланням; лог відправок (коли, кому, ким).
3. Nodemailer уже підключений для магік-лінків персоналу — інфраструктура є.
4. Reply-to = email менеджера, щоб відповідь клієнта йшла напряму продавцю.

Розмір: **L**

### 16b. Портал клієнта (простий)
**Чому:** логічне продовження 16 — якщо клієнт уже автентифікується магік-лінком, він може бачити не одну квоту, а свій кабінет. Фактично — зародок CRM з боку клієнта.

**Робити (мінімальний обсяг, свідомо простий):**
1. Логін по email (магік-лінк), окремий від логіну персоналу — **інший неймспейс сесій, ніякого доступу до адмінки**.
2. Список **своїх** документів (тільки FINAL, ніяких чужих компаній): номер, дата, сума, статус, valid until.
3. Перегляд квота в HTML + завантаження PDF + підпис (те саме, що в 16.1).
4. Картка «Ваш менеджер»: фото/ім'я, email, телефон, кнопка «Зв'язатися».
5. Реквізити компанії-продавця й документи (T&C, RSP terms).
6. Свідомо **не робимо** на цьому етапі: чат, оплату, тікети, історію сервісу, документи по машині.

Розмір: **L**

**Безпекові вимоги (спільні для 16 і 16b):**
- Портал не має жодного спільного шару авторизації з адмінкою; окремі cookie, окремий middleware-гейт.
- Клієнт бачить **тільки** документи своєї компанії й тільки FINAL/Signed.
- Rate limiting на запит магік-лінка (щоб не перетворилось на email-бомбер).
- Токени в БД зберігати хешем, не відкритим текстом.

### 17. Імпорт/експорт прайс-листа
**Чому:** *"If you want, I can create import/export tool"* — Джон одразу: якщо ціни міняються щомісяця, це робитиметься регулярно.

**Робити:**
1. Експорт усього каталогу в один XLSX: продукт, код, part number, опис + колонка ціни на кожен регіон/валюту.
2. Імпорт з попереднім переглядом: що зміниться, що нове, що зникло; підтвердження перед записом.
3. Версіонування прайсу: дата набуття чинності, історія; фіналізовані квоти не перераховуються (ціни вже зафіксовані в `DocumentItem.unitPrice`) — це вже так працює, треба лише підтвердити тестом.
4. Тільки ADMIN.

Розмір: **M**

### 18. Регіони / прайс-листи: нові ринки
**Чому:** обговорення India USD, Mexico (USD, іноді песо), дистриб'юторські ціни. Рішення на мітингу: **без автоконвертації по курсу**, явні ціни на кожен регіон.

**Робити:**
1. Підтвердити, що можна створити довільну кількість регіонів із власною валютою, ставкою податку, max discount, логотипом, адресою, банком (в основному вже є).
2. Додати тип регіону: `Entity` (продає сам) vs `Price list` (тільки набір цін, напр. India / Distributor).
3. Поле «max discount» вже є — вивести підказку в UI біля поля знижки («max 10%»), і показувати чому заблоковано.

Розмір: **S–M**

### 19. Win / Loss трекінг (легкий CRM)
**Чому:** Вейн: *"do you reckon we could track win/loss with this?"*.

**Робити:**
1. Статуси документа: `Draft → Sent → Won / Lost / Expired`, дата зміни, причина програшу (dropdown: ціна / строки / конкурент / бюджет / інше) + коментар.
2. Дашборд: конверсія по продавцю/регіону/продукту, середній чек, pipeline value.
